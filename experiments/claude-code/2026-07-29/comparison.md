# 3方式の比較

## 結果

| 比較項目 | 指示だけ | 仕様駆動 | 自律反復 |
| --- | --- | --- | --- |
| 最初に与えた情報 | 短いプロンプト | `spec.md` | `spec.md`、`test.md`、`progress.md` |
| 確認質問 | なし | なし | なし |
| Planレビュー | なし | あり | なし |
| コード修正の追加指示 | 1回 | なし | なし |
| 人による環境介入 | なし | なし | `npm ci`と再開 |
| 最終テスト数 | 16 | 18 | 29 |
| コード構造 | 状態、制御、DOM | 状態制御、DOM | 状態、DOM |
| 合計所要時間 | 約5分44秒 | 約8分41秒 | 約5分2秒 |

| Node.js 24での自動確認 | 成功 | 成功 | 成功 |
| ブラウザ主要操作の抜粋 | 成功 | 成功 | 成功 |
| ゲームクリアまでの通し操作 | 成功 | 成功 | 成功 |
| キーボードだけでの完了確認 | 未実施 | 未実施 | 未実施 |

## 観察

指示だけの方式は、最も早く初回のゲームを生成できました。ただし、時間、リセット時のタイマー、状態ラベルなど、短い指示に含めなかった完成条件で差が生じ、追加指示が必要でした。

仕様駆動方式は最も時間と費用がかかりました。実装前に曖昧さを減らせたため、実装後のコード修正指示は不要で、責務を細かく分けた構成になりました。

自律反復方式はテスト数が最も多く、型エラーも自分で修正しました。一方、許可コマンドと選択したコマンドが一致しないだけで停止しました。自律性を高めても、人が環境、権限、停止理由を確認する役割は残ります。

3方式とも、実施していないブラウザ確認を自動テストだけで完了扱いにはできません。本文では、生成後に人が確認する工程を独立した手順として扱います。
